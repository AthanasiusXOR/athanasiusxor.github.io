A program asks for a library by name. What runs is a library the vendor did not ship. People collapse that into one word. The word is doing too much work. There are two failures, and the repair for one does not close the other.

Hijacking is the wider failure. The program makes a request. The answer that arrives is a different file. The name was a real request. The file is a substitution. The plate at the top is that moment drawn as a chapel. The application sends for a scroll. The scroll that comes back is not the one the house kept.

Sideloading is the narrower failure, and it is the one a signature will not catch. A legitimate program, often signed, was written to load a library from beside itself. Someone brings that program and a foreign library together and starts the program. The program does what its author designed. The signature still names the vendor. The library does not.

## The name is a party

This field-post has already said that the covenants keep their own names. Abraham is not Sinai. Sinai is not the new covenant. The seed is a particular person, not a crowd that wears his name and counts itself as him. The technical error has the same shape.

A signed program is a true name. It identifies a vendor, a binary, and a history of who built it. The library that runs under that name is another party. An allow-list that blesses the host and never asks who answered has flattened two parties into one covenant. The name was real. The party that answered was not the party the name was for.

The two failures divide on how the wrong party arrives. Hijacking abuses the request. The program asked, and the answer was swapped. Sideloading brings the true program along and lets it do what it was built to do, which is to trust the library at its side. The host kept its name. That is the point. The name was never the whole covenant.

## What the owner should be able to see

The public claim stops at recognition.

A defender who can see loaded modules can ask a plain question. Does the vendor ship this library with this program? A library beside a known program, which the vendor does not ship, is the shape of sideloading. A program that received a different file than the one its request was for is the shape of hijacking. The record of a module load is where the question is asked. A list of signed programs is not, by itself, the answer.

The lookup order, the names of programs that fail it, and the making of a stand-in library do not belong on this field-post. They belong, when they belong at all, inside an authorized engagement with a scope and a way to undo the damage. The judgment belongs here. A control that trusts the name and ignores the party will pass a program that has already kept a stranger.

## One repair does not close the other

Collapsing the two words trains the wrong repair. Hijacking is a request answered by the wrong file. The repair asks whether an untrusted place was permitted to answer a request the system should have kept for a known party. Sideloading is a program designed to trust its own side. The repair asks what may sit beside a trusted host, and whether a signature was asked to vouch for a covenant it does not contain.

The folder these plates came from is called From Decrees to DLLs. The decree of God is not a figure for a loader. The decree is the purpose. The covenants are how that purpose is administered in history, each under its own name, until Christ. A program's name is a much smaller thing. It is still a name. It should be kept for the party it names.
